# CourtIQ v1.1 + v1.2 Roadmap

> Status: v1.0 is in the App Store submission pipeline as a fully-free
> launch (tip-jar paywall). This doc plans the 4 features that ship next.

## Sequencing

```
v1.0       (now)        Fully free launch, tip-jar paywall
v1.0.x     (as needed)  Bug fixes from real-user feedback
v1.1       (~3–4 weeks) Voice + Photo + Push  (engagement loop)
v1.2       (~6–8 weeks) Coach/Partner Mode    (viral mechanism)
v1.3       (~12+ weeks) Re-introduce paid gating, data-driven
```

Rationale: v1.1 features lower the typing/text-entry friction Begum
called out. v1.2 introduces the only realistic viral loop (a tennis
partner you already see twice a week is forced to install CourtIQ to
pair with you). After 3 months of free usage we have engagement signal
to decide *which* feature deserves paywalling.

## v1.1.A — Voice note → Match Journal

**Why:** Direct response to "çok yazı". 30 seconds of dictated audio
replaces 5 minutes of thumb-typing. Apple on-device dictation is free,
private, and Turkish-capable since iOS 16.

**Scope (~5–7 days):**
- Add `audioURL: String?` field to `MatchEntry` (SwiftData migration)
- New `VoiceNoteRecorder.swift` in `Core/Utilities/` — tap-and-hold
  mic button using `AVAudioRecorder` + `SFSpeechRecognizer` for
  on-device transcription
- `MatchJournalEntryView`: replace the pre/post text fields with a
  combined "voice or text" affordance: mic icon as primary CTA,
  small "type instead" link as fallback
- Audio files stored in App Sandbox `Documents/MatchAudio/`,
  filename = `<entry.id>.m4a`
- Playback button on the saved entry detail view
- Permissions: Add `NSMicrophoneUsageDescription` + `NSSpeechRecognitionUsageDescription` to Info.plist

**UX safety:** transcript shown immediately, user can edit before save.
Audio stays optional — typing fallback always visible.

**Files to touch:**
- `Core/Models/MatchEntry.swift` (add field + migration)
- `Core/Utilities/VoiceNoteRecorder.swift` (new)
- `Features/Matches/MatchJournalEntryView.swift` (recorder UI)
- `Features/Matches/MatchJournalDetailView.swift` (playback)
- `Info.plist` (mic + speech recognition permissions)

## v1.1.B — Photo attach to match entry

**Why:** Visual memory hook. A photo of the scorecard, the court, your
hitting partner — anchors the entry without text. Also: most journal
apps that succeed (Day One, Daylio) have photos as the primary visual.

**Scope (~3 days):**
- Add `photoFileNames: [String]` to `MatchEntry`
- `PhotosPicker` integration in `MatchJournalEntryView` (iOS 16+ native,
  no permission required since iOS 14)
- Stored in `Documents/MatchPhotos/<entry.id>/<n>.jpg` at JPEG 0.7
- Detail view shows a horizontal photo strip; tap for full-screen view
- Limit: 4 photos per entry (keeps storage and UI sane)

**Files to touch:**
- `Core/Models/MatchEntry.swift`
- `Features/Matches/MatchJournalEntryView.swift`
- `Features/Matches/MatchJournalDetailView.swift`
- New helper: `Core/Utilities/MatchMediaStore.swift`

## v1.1.C — Daily + weekly push notifications

**Why:** Re-engagement loop. The Match Journal only earns its keep if
users actually log matches; a gentle reminder after the user's
playing-time window (defaults to 20:30 local) doubles weekly log rate
in similar journaling apps (Day One, Strava reports 1.7×–2.4×).

**Scope (~4 days):**
- Use existing `NotificationManager` (already in `Core/Utilities/`)
- Two notification streams:
  1. **Daily nudge** (20:30 local): "Played today? Log it." — only
     fires if no entry created today AND user has ≥3 entries total
     (don't nag new users)
  2. **Weekly digest** (Monday 09:00 local): "Last week: 3 matches.
     Serve confidence +12%. Open to see." — generated from
     `MatchTrendDashboardView` aggregations
- Pre-ask sheet (already exists: `NotificationPreAskSheet.swift`)
  shown after 3rd match entry — never on first launch
- All notifications cancellable from Profile → Notification Settings
  (new sub-screen)

**Files to touch:**
- `Core/Utilities/NotificationManager.swift` (schedulers)
- `Core/Models/MatchEntryManager.swift` (trigger pre-ask after 3rd entry)
- New: `Features/Profile/NotificationSettingsView.swift`
- `ProfileView.swift` (NavigationLink to settings)

## v1.2 — Coach/Partner Mode (the viral one)

**Why:** Tennis is intrinsically two-player. The only realistic viral
mechanism for a niche solo-dev tennis app is one where you literally
cannot use the feature without your partner installing it. QR pair +
shared journal is the cleanest manifestation: zero account creation
overhead (Bluetooth proximity + ephemeral session), tangible immediate
payoff (see the same match from your opponent's eyes).

### Two phases, ship-independently

#### Phase 1 (~10 days) — Local session via QR

- Player A taps "Pair with opponent" → ephemeral session ID generated,
  QR code shown
- Player B scans QR → both phones now share a UUID session
- Each player runs through the same Quick Log (4 ratings + takeaway)
  privately
- After both submit, both phones show a side-by-side comparison:

  ```
                YOU       OPPONENT
  Serve        4 / 5     2 / 5  ← they thought your serve was weak
  Return       3 / 5     4 / 5  ← they respected your return more
  Movement     3 / 5     3 / 5
  Mental       4 / 5     2 / 5  ← they read tilt you didn't show
  ```

- Implementation: **MultipeerConnectivity** (built into iOS, no
  backend needed). Session data exists only on the two devices.
  Optional save into both Match Journals.

**Files (new feature folder `Features/CoachMode/`):**
- `CoachSession.swift` — MultipeerConnectivity wrapper
- `CoachPairView.swift` — QR generate + scan
- `CoachQuickLogView.swift` — parallel rating capture
- `CoachReveal.swift` — side-by-side comparison animation
- `Features/Matches/MatchesListView.swift` — entry point button

#### Phase 2 (~5 days, ship if Phase 1 traction is real)

- Async pairing via deep link (`courtiq://coach?session=XYZ`) so
  partners don't have to be physically present at submit time
- Anonymous "post-match insights" share — partner can ack/comment
  on each rating without writing a full reply

## What's deliberately NOT in this plan

- **AI/LLM features** — explicit pivot decision; manual + Swift Charts
  is the differentiator. Revisit at v2.0.
- **Social feed** — too much moderation overhead for a solo dev.
- **Cloud video analysis** — interesting but ~3 months of focused work
  and infinitely expensive at scale.
- **Cross-platform / Android** — wait for >5k iOS WAU before considering.

## Validation gates

Each version ships only if the prior one earns it:

- **v1.1 ships** if v1.0 reaches 50 weekly active users with ≥30%
  D7 retention. Below that, focus on fixing v1.0 instead.
- **v1.2 ships** if v1.1's voice-note feature is used in >40% of
  match entries (= text reduction worked) AND weekly active users
  ≥150. Below that, Coach Mode won't have enough density to feel
  alive.
- **v1.3 paywall re-introduction** is conditional on v1.2 retention.
  If WAU growth is healthy without paying users, optionally extend
  the tip-jar window another 3 months.
